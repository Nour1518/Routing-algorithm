# GRAPH ROUTING API

Version: 1.0
Framework: Flask
Default address: http://localhost:5000
Default port: 5000

## DESCRIPTION

The Graph Routing API provides a REST interface for:

* Generating different types of graphs
* Loading graphs from files
* Saving graphs to files
* Listing loaded graphs
* Getting graph information and structure
* Running shortest-path algorithms
* Selecting different A* heuristics
* Building Contraction Hierarchies
* Collecting algorithm execution traces
* Deleting graphs
* Providing graph and algorithm schemas for GUI integration

1. STARTING THE SERVER

---

Run the Python API file:

```
python api.py
```

The server starts on:

```
http://localhost:5000
```

Because the application uses:

```
host="0.0.0.0"
```

the API can also be accessed from another device on the same network using:

```
http://<SERVER_IP>:5000
```

## 10. GENERIC GRAPH

Purpose:

Creates a graph containing nodes without automatically generated edges.

Request:

{
"type": "generic",
"nodes": 100,
"directed": false
}

Parameters:

```
nodes
    Number of nodes.

    Minimum: 1
    Maximum: 100000
    Default: 100

directed
    Whether the graph is directed.
```

Default example:

{
"type": "generic"
}

This creates:

```
100 nodes
0 automatically generated edges
undirected graph
```

IMPORTANT:

A generic graph is mainly useful when edges are added through the Graph class or when testing graph structures.

## 21. DIJKSTRA

}

22. A*

---

Request:

{
"start": 0,
"goal": 99,
"algorithm": "a_star",
"heuristic": "euclidean"
}

A* supports the following heuristics:

```
zero
euclidean
geographical
haversine
manhattan
grid
chebyshev
octile
```

If no heuristic is specified, the API uses:

```
zero
```

IMPORTANT:

A zero heuristic makes A* behave similarly to Dijkstra in terms of its heuristic contribution.

23. BIDIRECTIONAL DIJKSTRA

---

Request:

{
"start": 0,
"goal": 99,
"algorithm": "bidijkstra"
}

No heuristic is required.

24. BIDIRECTIONAL A*

---

Request:

{
"start": 0,
"goal": 99,
"algorithm": "bi_a_star",
"heuristic": "euclidean"
}

Supported heuristics are the same as A*.

25. BFS

---

Request:

{
"start": 0,
"goal": 99,
"algorithm": "bfs"
}

BFS does not use edge weights when determining the route.

It is therefore appropriate mainly for unweighted graphs or when minimizing the number of edges is the objective.

26. CONTRACTION HIERARCHY

---

Request:

{
"start": 0,
"goal": 99,
"algorithm": "ch"
}

CH requires:

```
ch_ready = true
```

If CH has not been built, the request fails.

Build CH before routing:

```
POST /graphs/<graph_id>/ch
```

## 27. A* HEURISTICS

ZERO

Name:

```
zero
```

Returns:

```
0
```

Useful as a baseline.

EUCLIDEAN

Name:

```
euclidean
```

Uses:

```
sqrt((x1-x2)^2 + (y1-y2)^2)
```

Best suited to graphs where x/y represent Cartesian coordinates.

GEOGRAPHICAL

Name:

```
geographical
```

Uses the same Euclidean distance calculation as the "euclidean"
heuristic.

It uses:

```
x
y
```

coordinates stored in node data.

HAVERSINE

Name:

```
haversine
```

Calculates geographical distance on Earth.

The implementation assumes:

```
x = longitude
y = latitude
```

The returned distance is in meters.

This heuristic is intended for geographical coordinates such as:

```
longitude / latitude
```

MANHATTAN

Name:

```
manhattan
```

Uses:

```
|row1-row2| + |col1-col2|
```

It expects node data containing:

```
row
col
```

It is intended for grid graphs.

GRID

Name:

```
grid
```

Equivalent to the current Manhattan/grid heuristic.

It expects:

```
row
col
```

CHEBYSHEV

Name:

```
chebyshev
```

Uses:

```
max(|x1-x2|, |y1-y2|)
```

It expects:

```
x
y
```

OCTILE

Name:

```
octile
```

Uses:

```
max(dx,dy) + (sqrt(2)-1)*min(dx,dy)
```

It expects:

```
x
y
```

It is useful for grid-like movement where diagonal movement is allowed.

28. TRACE

---

The route endpoint supports optional search tracing.

Request:

{
"start": 0,
"goal": 99,
"algorithm": "a_star",
"heuristic": "euclidean",
"trace": true
}

If the corresponding visual algorithm exists in Graph, the API attempts to return the search trace.

The response contains:

```
"trace": [...]
```

If tracing is disabled:

{
"trace": null
}

Tracing is mainly intended for visualization and algorithm demonstrations.

It can increase memory usage and execution time.

29. ROUTE RESPONSE

---

Example:

{
"success": true,
"graph_id": "abc123",
"query": {
"start": 0,
"goal": 99,
"algorithm": "a_star",
"heuristic": "euclidean"
},
"result": {
"found": true,

"path": [
0,
4,
8,
15,
31,
99
],
"path_nodes": 6,
"path_edges": 5,
"path_length": 245.7
},
"trace": null
}

30. ROUTE RESULT FIELDS

---

found

Indicates whether a path was found.

```
true
false
```

cost

The cost returned by the Graph routing algorithm.

If no path exists:

```
null
```

time_seconds

Execution time measured by:

```
time.perf_counter()
```

This measures the routing operation performed by the API.

path

List of node IDs forming the resulting route.

Example:

[
0,
5,
12,
20
]

path_nodes

Number of nodes in the returned path.

path_edges

Number of edges in the returned path.

Usually:

```
path_edges = path_nodes - 1
```

path_length

Sum of edge weights found in the original graph.

For CH shortcut edges, path length may become:

```
null
```

because the shortcut may not directly exist in the normal adjacency structure.

HTTP:

```
404
```

Response:

{
"success": false,
"error": "Graph not found."
}

Possible cause:

The graph ID is invalid or the graph was deleted.

MISSING GRAPH TYPE

HTTP:

```
400
```

Response:

{
"success": false,
"error": "Missing 'type'."
}

INVALID GRAPH TYPE

Example:

{
"type": "unknown"
}

Response contains an error indicating the supported graph types.

INVALID ALGORITHM

Example:

{
"algorithm": "astar"
}

The valid name is:

```
a_star
```

MISSING START

Response:

{
"success": false,
"error": "Missing 'start'."
}

MISSING GOAL

Response:

{
"success": false,
"error": "Missing 'goal'."
}

INVALID FILE

If a requested file does not exist:

HTTP:

```
404
```

Example:

{
"success": false,
"error": "File not found: ..."
}

CH NOT READY

If:

```
"algorithm": "ch"
```

is requested before CH is built, the routing operation raises an error indicating that CH must be built first.

39. IMPORTANT IMPLEMENTATION NOTES

---

1. GRAPH STORAGE

Graphs are stored in memory:

```
GRAPHS = {}
```

They are identified using randomly generated UUID values.

The API does not provide persistent server-side graph storage by itself.

2. FILE PATHS

When loading or saving a graph, the filename is interpreted by the Flask server.

The client does not upload the file contents through this API.

The file must therefore be accessible from the server machine.

3. TRACE SUPPORT

Trace output depends on the corresponding visual method existing in Graph.

For example:

```
dijkstra_visual
a_star_visual
bidirectional_dijkstra_visual
bidirectional_a_star_visual
```

BFS and CH do not use the visual methods in the current API implementation.

4. A* HEURISTICS

The API selects a heuristic only for:

```
a_star
bi_a_star
```

Other algorithms ignore the heuristic parameter.

5. AUTOMATIC HEURISTIC

If no heuristic is supplied, get_heuristic() selects one based on graph_type.

Current automatic behavior:

```
geographical -> geographical heuristic
road         -> geographical heuristic
grid         -> grid/Manhattan heuristic
other        -> zero heuristic
```

6. DIRECTED GRAPHS

All generated graph types support:

```
directed: true
```

or:

```
directed: false
```

7. GRAPH STRUCTURE

The structure endpoint returns:

```
nodes
edges
```

Node data is returned exactly from the Graph node's data dictionary.

Example:

{

## 44. INTENDED ARCHITECTURE

The API is designed to separate the routing system into three layers:

```
Graph class
    |
    v
Flask REST API
    |
    v
Client / GUI / CLI
```

The Graph class handles:

```
Graph representation
Graph generation
Routing algorithms
Contraction Hierarchy
Graph serialization
```

The Flask API handles:

```
HTTP communication
Request validation
Graph identification
Algorithm selection
JSON serialization
Performance measurement
```

A GUI or CLI can therefore communicate with the graph system without directly manipulating the Graph object.
